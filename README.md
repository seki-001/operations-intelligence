# Operations Intelligence

A small, working internal tool that turns a shared operations spreadsheet into a
**validated, read-only dashboard** with a **reviewed weekly briefing**.

> **Demo project.** All sites, figures and events are fictional and generated by
> `scripts/generate_synthetic_data.py`. It is not built for or with any organisation's data.

**Live demo:** https://operations-intelligence-dashboard.onrender.com
(free hosting: the first load after a quiet period can take up to a minute while it wakes)

### Try it in 60 seconds

1. Open the live demo. It has already read the demo Google Sheet.
2. **Needs attention:** the rule-based findings, e.g. Lakeshore's uptime drop and Market Town's collections.
3. **Data quality** (bottom): the 7 deliberate errors in the sheet, each with its sheet row number.
4. **Briefing → Redraft:** a short summary that cites the fact behind each statement (hover a tag
   like `F1`). Enter a name and **Approve**: nothing is final until a person signs it off.
5. **Sync now** re-reads the sheet. If a sync ever fails, the last good data stays on screen.

## What it does

1. **Reads a Google Sheet (read-only).** It uses a service account with the `spreadsheets.readonly`
   scope, so it cannot change the sheet even if a credential leaks. A bundled CSV is used for local
   development.
   If a key isn't available, a shared-link mode reads a sheet shared as "Anyone with the link: Viewer"
   (suitable only for demo data; see [deployment](docs/deployment.md)). In production the service account
   would be attached to the cloud service, so no key is stored at all.
2. **Validates every row** before anything is calculated. Rows with errors (a missing value, a negative
   reading, an impossible date, a duplicate) are **rejected and listed with their sheet row number**.
   Suspicious rows are **flagged but kept**. Nothing is silently "fixed".
3. **Stores each sync as a snapshot.** If a sync fails (bad credentials, sheet moved, broken columns),
   the dashboard keeps showing the last good snapshot and says that the latest sync failed.
4. **Calculates everything in code.** Energy sold, collection rate, uptime, unsold-energy share and
   period-on-period changes are all calculated by tested functions. Simple, visible thresholds turn
   them into findings (critical / warning / info). Periods with missing days are marked as
   incomplete rather than shown as a fake drop.
5. **Drafts a briefing from those facts.** The model (or a template when no model is set up) receives
   only aggregated facts with IDs, never raw rows or customer data. It must cite a fact ID for every
   statement and keep *observed* separate from *possible explanations*. Every number in the output is
   checked against the facts, and any number it can't match is shown as a warning.
6. **Needs a named person to approve each briefing.** Drafts are saved as *awaiting review*, then
   approved or rejected by a named person.

## Design choices

| Concern | Choice |
|---|---|
| Source systems | Read-only access only; the tool never writes back to the sheet or to anything on site |
| Numbers | Calculated in code, never by the language model |
| AI | Any provider with an OpenAI-compatible API (Groq, Google AI Studio, OpenRouter, a local Ollama server), set by environment variables; easy to switch to an approved provider |
| No model configured | A clearly labelled template summary ("no AI model used"), never passed off as AI output |
| Secrets | Environment variables only; `.env` and key files are git-ignored; the API key exists only server-side (the browser never calls the API directly) |
| Failure | Failed syncs are recorded and shown, and never overwrite good data |
| Stack | Next.js + TypeScript, FastAPI + Python, SQLModel (SQLite locally, Postgres in production), Recharts. No microservices. |

## Run it locally (about 5 minutes)

```bash
# Backend
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env            # defaults use the bundled synthetic CSV
uvicorn app.main:app --reload   # http://localhost:8000/docs

# Frontend (second terminal)
cd frontend
npm install
cp .env.example .env.local
npm run dev                     # http://localhost:3000, then click "Sync now"
```

Tests: `cd backend && python -m pytest -q` (validation, analytics, AI guardrails, API, failure handling).

## API

All `/api/*` routes need the `X-API-Key` header.

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness check (public) |
| POST | `/api/sync` | Read the source, validate it, store a new snapshot |
| GET | `/api/sync/status` | Current snapshot and latest attempt |
| GET | `/api/overview?period_days=7` | Period comparison per site and for the portfolio, plus findings |
| GET | `/api/trends?metric=uptime_pct` | Daily series per site |
| GET | `/api/data-quality` | Rejected and flagged rows for the current snapshot |
| POST | `/api/reports/summary` | Draft a briefing (status: awaiting review) |
| POST | `/api/reports/{id}/review` | Approve or reject a briefing, with the reviewer's name |

## Not in scope (on purpose)

- A free-form chat assistant ("ask your data"). The next step would be one that answers only with
  queries run in code and shows the query behind each answer.
- Writing back to any system. Changes to billing or finance would go through the people who own them
  (e.g. FP&A sign-off).
- Multi-user login. Single sign-on with role-based access (e.g. Google Workspace) is the obvious
  production path.
